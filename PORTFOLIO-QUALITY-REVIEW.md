# Portfolio Quality Review — Working Branch

**Review date:** 9 November 2026  
**Reviewed branch:** `project/mindcommons-ai-framework`  
**Scope:** Repository tree, landing-page positioning, portfolio structure/status, opportunity map, core project folders, research samples and MindCommons AI documentation.  
**Important:** This is a documentation and navigation audit, not a technical security audit or independent verification of every factual claim in every research sample.

## 1. Overall assessment

The repository has a credible shared direction when presented as:

**Technology Researcher & Technical Documentation Specialist — focus on AI systems, responsible technology and digital policy.**

The strongest common thread is researching a technology problem, analysing the system and its implications, then documenting a practical, responsible approach. Technical writing is the communication method supporting that work, not a separate unrelated identity.

The repository should remain one master portfolio. Applications should select evidence from it rather than create separate portfolios for each opportunity.

## 2. Changes made in this review

- Reframed MindCommons AI as a **Community Data-Use Accountability Ledger** rather than a broad data-commons platform.
- Limited the product to three capabilities: approved-use record, change-of-use review and community-obligation follow-up.
- Removed assumptions that it needs a new consent portal, researcher management portal, governance body, generic dashboard or participant-data repository.
- Made the AI assistant contextual to the three tasks, with source-linked explanations and no decision authority.
- Updated the research, product definition, MVP, architecture, product experience, dashboard layout and sources register.
- Updated the Mozilla host research and opportunity evidence map to reflect the narrowed proposal.
- Preserved the distinction between public evidence and unverified internal workflows.
- Kept the working branch separate from `main`.

## 3. MindCommons AI — audit conclusion

### What is strong
- The proposal is now much smaller and easier to explain.
- It recognises SRHIN's existing Gencurate, LEWG, ethics oversight, charters, SOPs and public community-governance resources.
- It addresses a specific lifecycle question: how one approved use, later changes and community-agreed obligations are connected.
- The AI has defined tasks and firm limits.
- The architecture avoids assuming an integration or copying sensitive participant data.

### What remains unproven
- Whether SRHIN already has an internal register or workflow that handles this lifecycle.
- Whether community stewards experience this as a real problem.
- Whether the host challenge's exact wording is reproduced accurately in the third-party source. The original Mozilla RFP PDF still needs direct review.
- Whether a separate interface would improve the process or add duplicate administration.

### Decision
**Proceed with research and host/community validation only. Do not build a prototype now.** If existing workflows already solve the problem adequately, stop or redirect the concept.

## 4. Repository-level quality observations

### Strengths
- The main README and portfolio structure now state one professional direction.
- Vantage Automata, Jarvis AI and MindCommons AI can be explained as connected examples of AI systems analysis, product/system thinking and responsible design.
- The opportunity map records seven active targets and explains gaps rather than claiming universal fit.
- Portfolio status distinguishes documented concepts from working implementations and genuine contributions.
- MindCommons now has a coherent research → definition → MVP → architecture → experience → references sequence.

### Items to improve in a later focused cleanup
1. **Legacy top-level sample files:** Several project sample files remain at repository root, including filenames with a trailing newline character. These should eventually be moved/renamed into `technical-guides/` and their links repaired. They were not deleted or renamed in this pass to avoid accidental loss.
2. **Technical-writing sample consistency:** Review each sample for a clear brief, intended audience, source/product accuracy, revision evidence and a short note explaining what the sample demonstrates.
3. **Cloud infrastructure and n8n material:** Keep these as research/documentation samples, not claims of deployed automation or engineering implementation.
4. **Project status labels:** Continue applying the same labels—research, concept, proposed design, working demonstration, tested, deployed—consistently across Vantage, Jarvis and MindCommons.
5. **Opportunity currency:** Recheck opening dates, eligibility and programme details before each application. The opportunity map is a planning document, not a guarantee that every programme is currently open or that the applicant meets every criterion.
6. **Open-source evidence:** A contribution guide is not an upstream contribution. Add issue/PR links only after actual submission and record their real status.
7. **Internet governance strand:** It remains a development priority until the planned learning and a focused issue brief are completed.

## 5. Evidence and claims standard

The repository should never imply:
- Professional software engineering or production deployment without evidence.
- Working integrations where only a proposed architecture exists.
- Host endorsement, partnership or access to internal systems.
- Community consultation, user testing or co-design that has not occurred.
- A verified organisational gap based only on the absence of a public webpage.
- An upstream open-source contribution that has not been submitted.

## 6. Recruiter-facing interpretation

A recruiter should see a developing technology research and technical documentation profile with a focus on AI systems and responsible technology. They should not be led to infer that the applicant is a data-entry specialist, professional software engineer, clinical practitioner or experienced policy specialist.

The strongest next evidence is not another new concept. It is deeper quality in the existing research and documentation samples, one genuine open-source contribution, and practical implementation evidence only where the user chooses to build and can verify the result.

## 7. Final status

The repository is more coherent after this pass, but it is **not yet a fully polished final portfolio**. The remaining root-file organisation and sample-by-sample quality review are real cleanup tasks. This review deliberately avoids a risky mass move or deletion of existing files.
